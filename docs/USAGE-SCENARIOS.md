# Memcarry 실전 사용 시나리오

> 필요한 기억을 남기고, 다음 작업으로 잇는다.

이 문서는 **한 PC에서 Codex·Claude·Gemini·AGY를 사용하는 개발자**를 위한 예시다.
worktree 운영은 다루지 않지만 기존 격리 기능은 그대로 유지된다.

## 빠른 선택

| 수준 | 상황 | 요청 예시 |
| --- | --- | --- |
| 기본 | 결정과 이유 보존 | “이 결정과 이유를 memcarry에 남겨줘.” |
| 기본 | 다음 날 재개 | “memcarry 기록과 실제 파일을 확인하고 이어가자.” |
| 기본 | 긴 대화를 새 세션으로 전환 | “다음 세션에 필요한 진행 상태를 남겨줘.” |
| 기본 | 과거 판단 조회 | “memcarry에서 이 방식을 포기한 근거를 찾아줘.” |
| 응용 | 다른 AI로 교대 | “다음 AI가 이어받도록 memcarry에 인계 내용을 남겨줘.” |
| 응용 | 리뷰를 수정으로 연결 | “리뷰 기록을 확인하고 재현 테스트부터 만들자.” |
| 응용 | 예기치 않은 중단 | “마지막 저장 기록과 현재 변경 사항을 대조해줘.” |
| 전문 | 성능 실험 축적 | “조건·측정값·해석·채택 여부를 구분해 남겨줘.” |
| 전문 | 장기 버그 조사 | “확인한 사실과 미검증 가설을 구분해 이어가자.” |
| 전문 | 릴리스 준비 | “구현·검증 기록과 실제 변경 사항으로 릴리스를 점검하자.” |

위 문장은 **설치된 skill을 agent에게 사용하도록 요청하는 자연어 예시**다.
문자열을 감지하는 전용 키워드나 `memcarry save` 같은 CLI 명령이 아니다.
저장·읽기 실행에 필요한 권한과 도구가 해당 agent에 있어야 한다.

## 시작 전 확인

```bash
npx --allow-git=all -y github:al-hub/memcarry install --agents all
npx --allow-git=all -y github:al-hub/memcarry status --agents all
```

현재 배포 경로는 GitHub다. `@al-hub/memcarry`의 npm 공개를 가정하지 않는다.
기존 설치 사용자는 먼저 [이름 전환 안내](MIGRATION-MEMCARRY.md)를 읽는다.

- `status`의 `hooked`는 설정 파일에 hook이 있다는 뜻이지, 실제 AI가 문맥을 소비했다는 증명은 아니다.
- SessionStart는 저장된 L2를 불러오고 연속성 판정용 checkpoint를 갱신한다.
- **작업 내용 전체를 자동 저장하지 않는다.** 목표·완료 사항·남은 일은 durable memory로 실제 기록해야 한다.
- checkpoint는 마지막 세션·agent·Git 상태의 관측값이다. 대화 원문이나 모든 작업 내용을 담는 백업이 아니다.
- 새 세션이나 `/clear` 이후 hook 실행 여부는 실제 CLI 지원과 설정에 달려 있다. 불러온 내용이 없으면 skill의 수동 recall 경로를 사용한다.

## 1. 기본방식 — 같은 AI와 계속하기

### 1-1. 중요한 결정 남기기

**상황:** Python startup 최적화 실험 결과를 나중에도 활용하려 한다.

**사용자 요청**

> 두 번의 A/B에서 명확한 개선이 없었으니 fast-path 중복 구현은 보류하자.
> 실험 조건, 결과 파일, 판단 이유를 memcarry에 남겨줘.

**저장 후 확인할 것**

- 저장 ID와 프로젝트 범위가 확인되었는가?
- “효과 없음”이라는 결론이 어떤 환경·측정 조건에 한정되는지 적혔는가?
- 실제 실행 결과와 AI의 해석이 구분되었는가?

**효과:** 같은 접근을 새 아이디어처럼 다시 시도하는 낭비를 줄인다.
환경이 바뀌면 예전 결론을 절대 규칙으로 쓰지 않고 재검토한다.

### 1-2. 오늘 하던 일을 내일 이어가기

**오늘**

> 여기까지 memcarry에 저장해줘. 완료 사항, 남은 문제, 다음 작업, 테스트 결과를 포함해줘.

**내일 같은 프로젝트에서 새 세션 시작**

> memcarry 기록을 확인하고 실제 파일·Git 상태와 대조한 뒤 다음 작업부터 계속하자.

**성공 기준:** 저장된 맥락이 제공되고, 현재 상태 확인 후 올바른 다음 행동을 선택한다.
`RESUME`이라는 모드 이름만 출력되는 것으로 성공을 판단하지 않는다.

### 1-3. 대화가 길어져 새 세션으로 넘어가기

**기존 세션**

> 새 세션으로 넘어가려고 해. 목표, 결정, 수정 내용, 미해결 문제를 memcarry에 남기고 저장 결과를 알려줘.

**새 세션**

> 저장된 진행 상태를 확인하고 이어가자. 저장되지 않은 내용은 추측하지 마.

**주의:** 저장 성공을 확인한 뒤 세션을 초기화한다. 모델 내부 상태의 완전 복원은 아니다.

### 1-4. 과거 판단만 찾아보기

> memcarry에서 scope-first FTS를 선택한 이유와 당시 검증 결과를 찾아줘.

**성공 기준:** 질문에 관련된 결정·근거를 제시한다. 과거 작업 전체를 재개하거나 파일을 수정할 필요는 없다.
기록이 없으면 “찾지 못했다”고 알리고 답을 지어내지 않는다.

## 2. 응용방식 — AI를 바꾸며 이어가기

### 2-1. Codex 구현 → Claude 리뷰 → Gemini 문서화

| 순서 | 사용자 요청 | 넘길 내용 |
| --- | --- | --- |
| Codex | “Claude가 리뷰하도록 memcarry에 인계를 남겨줘.” | 목적, 주요 파일, 결정, 테스트 결과, 걱정되는 부분 |
| Claude | “인계를 확인하고 코드·테스트로 검토해줘.” | 재현된 문제, 의심 사항, 검토하지 못한 범위 |
| Gemini | “구현·리뷰 기록을 실제 코드와 대조해 문서화해줘.” | 확정 기능, 제한 사항, 실행 가능한 사용 예시 |

같은 프로젝트와 같은 L2를 사용한다. 저장된 agent identity가 바뀌면 `HANDOFF`가 선택될 수 있다.
AI 종류에 고정된 역할은 없으며 순서는 바꿔도 된다.

**주의:** 이전 AI의 판단은 검토 근거이지 정답이 아니다. 인계는 파일 복사나 Git 병합을 대신하지 않는다.

### 2-2. 리뷰 결과를 TDD 수정으로 연결하기

**리뷰 AI**

> 문제를 확정된 오류와 추가 확인이 필요한 의심으로 나눠 memcarry에 남겨줘. 재현 조건도 포함해줘.

**구현 AI**

> 리뷰 인계를 확인하고 오류를 재현하자. 실패 테스트를 먼저 만들고 수정한 뒤 전체 테스트를 실행해줘.

**성공 기준:** 리뷰 요약뿐 아니라 재현 조건과 검증 상태가 전달된다.
수정·commit·push는 해당 사용자 요청의 허용 범위 안에서 별도로 수행한다.

### 2-3. 오류·한도로 이전 AI를 쓸 수 없을 때

**다른 AI에서 같은 프로젝트 실행**

> memcarry에 남은 기록을 확인해줘. 확실한 완료 사항과 불확실한 부분을 나누고 실제 변경 사항을 대조하자.

**효과:** 마지막 저장 지점부터 조사와 작업을 이어갈 수 있다.
마지막 저장 이후의 대화는 누락될 수 있으며 디스크 손상 복구나 원격 백업 기능은 아니다.

## 3. 전문활용방식 — 작업 절차에 기억 포함하기

### 3-1. 성능 실험을 여러 세션에 걸쳐 진행하기

1. **기준 측정:** 환경·버전·데이터 크기·실행 명령·p50/p95·결과 파일을 남긴다.
2. **개선 실험:** 동일 조건에서 변경 전후를 비교한다.
3. **판단 기록:** 개선 여부와 불확실성, 채택·보류 이유를 남긴다.
4. **다음 세션:** 기존 실험을 확인하고 미검증 가설부터 진행한다.

> 이번 측정의 조건, 결과, 해석을 분리해서 memcarry에 저장해줘. 원본 결과 파일 위치도 남겨줘.

**성공 기준:** 실패한 실험과 측정 조건을 재사용한다. 실행 시간의 정확한 일치나 환경이 다른 수치의 우열을 주장하지 않는다.

### 3-2. 장기 버그 조사를 교대로 진행하기

> 재현 조건, 확인한 사실, 배제한 원인, 미검증 가설, 다음 실험을 나눠 memcarry에 남겨줘.

다음 AI는 기록을 읽고 다음 미검증 실험부터 진행한다.
코드나 환경이 달라졌다면 이전에 배제한 원인도 다시 검토할 수 있다.

**성공 기준:** 가설이 반복 인계를 거치며 확정 사실로 바뀌지 않는다.
`verified`는 실제 근거가 있을 때만 지정하고 나머지는 불확실성을 유지한다.

### 3-3. 릴리스 준비 이어가기

| 단계 | 기록할 것 | 다음 단계의 확인 |
| --- | --- | --- |
| 구현 | 변경 범위·테스트·제한 | 실제 diff와 일치하는가? |
| 검증 | 통과·실패·미실행 항목 | 미확인을 통과로 잘못 표시하지 않았는가? |
| 문서화 | 확정 기능·설치법·주의점 | 실제 명령과 동작하는가? |

> 저장된 구현·검증 기록과 실제 변경 사항을 대조해서 릴리스 준비 결과를 정리해줘.

Memcarry는 CI 실행기·승인 시스템·감사 원장이 아니다. 각 단계의 사실과 다음 행동을 연결한다.

## 저장과 불러오기의 실제 경로

예를 들어 이 저장소의 **현재 remote identity**가 `github.com/al-hub/memcarry`라면:

```bash
python3 ~/.memcarry/runtime/scripts/memcarry_store.py add \
  "두 차례 A/B에서 명확한 개선이 없어 fast-path 중복 구현을 보류했다." \
  --type decision --status confirmed \
  --scope repository --scope-ref github.com/al-hub/memcarry \
  --source-agent codex --source-type project-file \
  --source-pointer docs/continuity-e2e-startup-alpha17.md
```

`scope-ref`는 예시 문자열을 그대로 복사하지 말고 **실제 프로젝트의 canonical repository ID**로 지정한다.
skill은 `GitRepositoryInspector`로 ID를 확인한다. 저장기의 기본 scope는 `global`이므로 프로젝트 기록에서 생략하지 않는다.
기존 origin이 옛 주소라면 해당 ID도 옛 주소이며, 자동 재지정하지 않는다.

```bash
python3 ~/.memcarry/runtime/scripts/continuity_context.py \
  "이전 startup 실험의 결정 근거를 찾아줘" --cwd "$PWD" --json
```

일반 조회는 기존 세션 문맥을 유지한다. 새 세션에서 수동 재개할 때만 실제 상황에 맞게 `--empty-session`과 `--session-id`를 사용한다.
사용자 지정 저장 경로라면 두 명령 모두 `--home`을 지정하거나 `MEMCARRY_HOME`을 설정한다.

## 기대하면 안 되는 것

- 모든 대화나 모델 내부 기억의 자동·완전 보존
- 저장 요청만 했는데 실행 없이 저장되었다는 보장
- 다른 PC·다른 계정으로의 자동 동기화
- 기록에 적힌 테스트 결과가 현재 HEAD에서도 통과한다는 보장
- 미구현 `memcarry save`, `memcarry resume`, `memcarry handoff` 명령
- 저장만으로 자동 구현·commit·push까지 허가되는 동작

**실용성의 기준은 “얼마나 많이 저장했는가”가 아니라 “다음 작업자가 근거를 확인하고 제대로 이어갈 수 있는가”다.**
